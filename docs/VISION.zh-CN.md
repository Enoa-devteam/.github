## 1. 我们希望构建什么

**以对话为接口，以工程实践为目标。**

聊天机器人擅长理解不完整的自然语言请求、保持上下文和降低交互门槛；Coding Agent 擅长在软件工作区内阅读代码、修改文件、执行测试、交付工程产物。二者各有职责，不应该相互伪装。

**Enoa 的方向是将两者有机结合，构建真正具备工程任务处理能力的聊天机器人。** 用户可以自然表达意图，而不必记住每项工具的命令格式；系统则根据任务类型，给出解释，或在授权边界内执行并反馈可核验的结果。

最重要的区分是：**讨论一项操作，不等于授权执行这项操作。** 系统必须既能理解语义上的区别，也能在执行阶段切实落实。

目前我们正在建设支撑该愿景的独立模块，并不宣称已完成通用自主软件工程师。

## 2. 理想系统需要具备的能力

1. **理解对话：** 保留必要的上下文与记忆，不依赖无限增长的 Prompt。
2. **合理分工：** 在直接回复、确定性工具、澄清问题和多步骤 Coding Agent 任务之间选择。
3. **区分判断与授权：** 模型或路由器可以提出执行建议，最终必须由可信宿主策略准入。
4. **有边界地执行：** 限定工作区、权限、可用工具、时限、资源预算以及副作用。
5. **用证据反馈：** 区分已尝试、成功、部分成功、失败与状态未知，并附上相应检查和产物。
6. **可预测地恢复：** 服务中断或返回结果不明确时，不应盲目重试副作用操作，更不能声称已经成功。

调用 Agent 的次数不是目标。普通问答应继续作为普通对话处理；确定性短任务不应被升级成昂贵的长时编码任务。

## 3. 参考架构

下面展示的是**目标协作关系**，而不是当前所有仓库均已完成集成的证明。

~~~text
用户 / 聊天平台
       |
       v
可信宿主边界
（身份、消息来源、上下文、现有授权）
       |
       v
Stella —— 对话与编排
       |
       +--> 对话 / 记忆 / 自然语言回复
       |
       +--> 现有 Capability Router --> Comes / 工具提供者
       |                                  |
       |                                  +--> 本地工具和插件
       |                                  +--> 可接入的 Ligamina MCP 工具
       |
       +--> [规划接入] Alcor 语义决策建议
                  （对话 / 澄清 / 委派 / 弃权）
                           |
                           v
                   宿主执行准入
            （请求绑定、权限、工作区、
             执行配置、后端健康检查）
                           |
                         准入后
                           v
                  Cometa / Coding Agent
                      （受限工作区）
                           |
       +-------------------+-----------------+
       |                                     |
       v                                     v
   工具执行结果                        Agent 产物 / 测试
       |                                     |
       +-------------------+-----------------+
                           |
                           v
                   验证与结果溯源
                           |
                           v
                    以对话反馈用户
~~~

**特别说明：** Stella → Alcor 及其后续准入链属于规划中的集成；图中 Ligamina 的 MCP 能力已经有独立实现，但不表示 Stella 与 Ligamina 已完成端到端接线。

### 各模块的职责边界

| 模块 | 主要职责 | 不应该承担的职责 |
| --- | --- | --- |
| **Stella** | 对话、记忆、上下文、能力路由、结果表达以及宿主侧约束 | 因为用户正在聊天，就把消息解释成无限制执行命令 |
| **Alcor** | 根据可信上下文，建议对话、澄清、弃权或委派 Coding Agent | 发放权限、批准操作、提供工作区授权或直接执行任务 |
| **Cometa / 外部 Coding Agent** | 在通过准入之后处理代码检查、修改、测试等多步骤工程任务 | 自行授予执行权限 |
| **Ligamina** | 保留 Koishi、NoneBot、AstrBot 的原生插件运行机制，提供 MCP 风格工具面与版本绑定的兼容性测试证据 | 保证所有第三方插件一定安全、一定兼容 |
| **可信宿主 / 准入策略** | 确定用户身份与来源请求、检查授权范围、执行配置与幂等性 | 将模型生成的“已授权”作为权限事实 |

“可信宿主”表示**责任边界**，不一定要新建一个独立服务。检查逻辑可以分布在现有模块中，但最终权限不能交由模型输出决定。

## 4. 需要明确区分的三类请求

| 请求意图 | 推荐处理方式 | 示例 |
| --- | --- | --- |
| **讨论、解释** | 直接聊天，不触发工程执行 | “为什么这个测试可能不稳定？” |
| **检查、查询** | 使用合适的只读工具，或在授权范围内进行受限的代码检查 | “检查这个仓库，找出失败的测试。” |
| **修改、操作** | 先核对明确授权和作用范围，未满足条件则澄清或拒绝执行 | “在这个工作区修复问题，并运行测试。” |

类似“就按刚才的方案做”的回复，可以引用一个**具体、有效**的待执行方案，却不是无限权限许可。宿主需要重新核对方案的所有者、版本、目标、上下文关联以及授权是否仍然有效。引用内容、其他用户的消息、Agent 自己的建议均不能直接构成授权。

更换本地或在线模型，不应悄悄改变这些规则。

## 5. 执行与信任边界

目标架构应满足以下约束：

- **可信来源：** 用户身份、消息来源、工作区绑定和授权来自宿主认证后的状态，而不是模型对聊天内容的猜测。
- **建议不是命令：** Alcor 的推荐可以被宿主拒绝；不确定或弃权结果不能被升级为执行请求。
- **只读不等于可写：** 检查与修改任务使用分开的受限配置，分别核验权限。能访问工作区不代表能够改写工作区。
- **任务必须有边界：** 执行器只获得具体目标、许可范围、预算、截止条件与稳定来源标识；重复提交沿用原有幂等身份。
- **工具输出不可信任：** 插件、仓库文件、检索文档和 Agent 输出都属于低信任数据；工具必须按白名单暴露，结果需要验证，不能反过来扩大权限。
- **如实报告状态：** 超时、取消、部分成功、失败、未知与确认成功不能混淆；状态不明时先查询记录，不盲目重放副作用操作。
- **控制上下文：** 不把全部工具 Schema、执行日志或 Agent 轨迹塞进 Stella 主对话窗口；对话层接收有来源标记的有界摘要，完整证据在独立位置保存。
- **隐私与本地化：** 本地优先是一种可选部署方式，不代表任何配置下都绝对不出网。在线模型、外部 Coding Agent、平台连接和联网插件应分别声明数据边界。

以上是**完整集成系统的目标约束**；每个子项目具体已实现并验证的部分，以自身代码、契约和测试记录为准。

## 7. 实施与验收路径

我们建议按照**证据驱动的门禁**推进，而不是一次性承诺完整自主执行能力。

| 阶段 | 必须能够证明的事项 |
| --- | --- |
| **A. 协议和本地基线** | 固定版本的接口、确定性契约测试、负样本、失败与超时语义 |
| **B. 决策质量和影子模式** | 人工裁决数据集、误委派统计、**不增加副作用**的影子预测 |
| **C. 受控只读工作流** | 真实只读沙盒、可信身份与范围检查、端到端结果归属、回退能力 |
| **D. 受控写入工作流** | 明确授权及必要审批、受限可写配置、可复现测试、幂等恢复、审计与回滚 |
| **E. 插件与真实平台验证** | 固定版本的插件行为覆盖率、独立的平台投递验收；不能凭少量试点宣称全面兼容 |

每一阶段都记录**验证过什么、尚未验证什么、出现什么情况需要撤销准入**。API 单测通过，不代表模型质量、真实沙盒或平台投递已经获得验证。

## 8. 非目标与取舍

Enoa 不绑定某一个模型提供商、Coding Agent 产品、Chatbot 框架或单一操作系统。模块边界的清晰与可复用，比把所有能力塞进同一进程更重要。

我们不追求把所有消息都解释成执行指令，不自动赋予文件系统与网络权限，也不把“发现插件”当作“兼容性得到证明”。

资源效率、本地部署、扩展性、稳定性与安全性之间存在现实取舍。相关决策应保留依据、反例及验证结果，并将实验性能力与发布承诺分开。
